# Brief — F4: the cel look renders the skinned character black

You are the implementer. Read `AGENTS.md` first — it is the shared contract and
it holds without amendment. Read `docs/MCGROTS-ROADMAP.md` § 10 fault F4 for
the history. This brief adds one thing that document does not have: a control.

**You own `src/mcgrots/looks.js`.** Codex is working in `scripts/rig-glb.mjs`
and `assets/characters/` at the same time. Do not touch those, and do not touch
`src/` outside `src/mcgrots/`.

## The fault

Under `?look=inked` and `?look=aerial` the character renders as a featureless
black blob. Every other object in the same frame — van placeholder, both seat
ledges, statue plinth, merged massing — cel-shades correctly.

## The control (new, measured 2026-08-11 — this is the useful part)

The capsule body and the skinned body take the **same** `looks.js` material.
Under identical `?look=inked`, same anchor, same frame count:

```bash
node scripts/mcgrots-shot.mjs --look=inked --anchor=counter --frames=600 --shot=/tmp/capsule.png
node scripts/mcgrots-shot.mjs --body=skinned --archetype=rab --look=inked --anchor=counter --frames=600 --shot=/tmp/skinned.png
```

The capsule renders cream, two-band, ink-outlined — correct. The skinned figure
renders solid black. Both captures were opened and inspected. Because the only
difference between the two arms is skinning, this isolates SkinnedMesh from the
cel material in a way the roadmap's earlier rulings did not: those compared the
figure against *other objects*, which differ in more than one respect.

Reproduce both before you change anything, and say in your report what you saw.

## Do not re-derive these

Each was visually confirmed. Re-testing them is wasted time:

| Suspect | Evidence against |
|---|---|

| the shade band | `SHADE_BAND` 52 vs 130 changes nothing |
| the albedo | same texture reads fine in `none-a.png`, same run |
| the lighting | same lights, same frame, same instant |

## Suggested first moves, cheapest first

`looks.js` builds the cel material as `MeshToonMaterial` plus an
`onBeforeCompile` injecting the aerial ramp, plus a constant
`customProgramCacheKey`.

1. Render with `onBeforeCompile` removed entirely, and **look at the picture**.
2. Then with `customProgramCacheKey` removed, and look.
3. Then check whether `MeshToonMaterial` + `USE_SKINNING` is picking up a
   wrongly-cached program.

A constant `customProgramCacheKey` across materials that compile to different
programs is the shape of bug that produces exactly this symptom, so step 2 is
where I would put my money — but measure, do not agree with me.

## A warning that has already cost a session

A bisecting probe was written for this and **contradicted itself between runs**
— same variant, cast mean 15.5 then 1.8. Its metric isolates the actor by
hiding it and diffing, which collapses to a tiny biased sample precisely when
the figure is dark. That metric is sound for comparing two grades and unsound
as an absolute. **Verify F4 with pictures, not with that metric.**
