# park-manifests — the generated index that makes the library navigable

Read `docs/briefs/park-CONTEXT.md` first.

## What you own

In the **library** repo (`/Users/dan/code/personal/mcgrot-assets`):

- everything under `manifests/`
- `tools/build-manifests.mjs` — the script that generates them
- `manifests/README.md` — how to read a manifest and how to regenerate

Nothing else. The `tools` unit owns the rest of `tools/`; coordinate by staying
inside those three paths.

## Why this unit exists

Every asset is named by an opaque hash. `0021ea9d.jpg` tells a reader nothing.
Dan chose to **keep it that way** — renaming 557 files is 557 chances to break
the comic-to-reading pairing, which is carried by the shared filename stem and
by nothing else.

So the meaning has to live somewhere else, and that somewhere is `manifests/`.

> **Browsing this library starts at a manifest, not at a directory listing.**
> Your output is what makes that true.

## What to build

A set of JSON manifests, one per asset class, generated by a script that can be
re-run. Generated, not hand-written — a hand-written index goes stale the first
time an asset is added.

At minimum:

- `manifests/sounds.json` — the 162 mp3s across `readings/`, `cast/`,
  `mcgrot/`. For a reading, the comic it belongs to is the key fact.
- `manifests/comics.json` — the Drive corpus. **The files are not on disk here**
  and are gitignored deliberately. This manifest is the tracked record of what
  exists on Drive: identifier, title if known, whether a reading exists for it,
  and whether it is in the game. Derive it from `data/catalog.json` and
  `data/readings.json`, not from a Drive listing.
- `manifests/visual-2d.json` and `manifests/visual-3d.json` — faces, façades,
  named comics; characters, vehicles.
- `manifests/index.json` — a small top-level roll-up: each class, its file
  count, its total bytes, and which manifest describes it.

## Every entry should carry

- **The filename**, exactly as on disk. Never a modified form.
- **Its path** relative to the library root.
- **Size in bytes**, and a **content hash** (sha256 is fine). The hash is what
  lets a future session prove a file is intact, and lets the validation unit
  check the library against its own manifest.
- **What it is**, in human terms, wherever a source record can tell you —
  `data/catalog.json`, `data/readings.json`, `data/comic-lines.json`,
  `data/businesses.json`, `data/facade-registry.json`, `data/manifest.json`.
- **Its provenance** where known: photographed, AI-generated, hand-made,
  derived from another asset. `visual/2d/facades/` has stages that record this
  — `raw`, `generated`, `handmade`, `borrowed`.
- **Its pairing**, where one exists. This is the load-bearing field. A reading
  must name its comic. A comic must say whether a reading exists.

## The pairing is the point — verify it

The comic-to-audio join is the single most fragile thing in this library. Your
manifest is what makes it legible and what will detect it breaking.

Check, and **report the real numbers**:

- How many `sounds/readings/*.mp3` stems have a matching comic in the catalogue.
- How many do not. **Name them.** An orphan is a finding, not an error to
  suppress.
- How many catalogue entries claim audio that does not exist. This is a known
  trap with a live incident behind it — an entry claiming a missing mp3 404s
  every time that station is opened. `CLAUDE.md` records that the generator was
  fixed and the merger was missed.

Do not "fix" any mismatch you find. Record it, in the manifest and in your
report. A wrong pairing quietly repaired is a fact destroyed.

## The script

`tools/build-manifests.mjs`, run from the library root, regenerating everything
under `manifests/`. Plain Node, no dependencies beyond what is built in — the
library must not need an `npm install` to be readable.

- Deterministic: two runs on unchanged input give byte-identical output. Sort
  every array by a stable key; do not let filesystem order leak in.
- `--check` mode that verifies the existing manifests against what is on disk
  and exits non-zero on a mismatch, printing what differs. The validation unit
  will use this, and so will anyone wondering whether the library is intact.
- Prints a summary: counts per class, total bytes, pairing statistics, and any
  orphans.

## Verify before you finish

Run these, and paste the real output into your report:

1. `node tools/build-manifests.mjs` — clean run, with its summary.
2. Run it **twice** and diff the output. Byte-identical, or it is not
   deterministic. Say which you observed.
3. `node tools/build-manifests.mjs --check` — passes on a clean tree.
4. **Fault-inject it.** Rename one file temporarily, confirm `--check` goes red
   and names that file, then restore it. A check that has never gone red is
   decoration. **Commit before injecting** — `git checkout <paths>` restores
   nothing if any path in the list is untracked.
5. Count check: the manifests between them account for every tracked file in
   `sounds/`, `visual/` and `data/`. State the number and how you derived it.
